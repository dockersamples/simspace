# Exploration: a `slides` content kind alongside labs

**Status:** Exploration / pre-decision. Nothing implemented.

## 1. What we're after

A workshop is usually _slides then hands-on_. Today the app only knows how to
serve labs, so the deck lives somewhere else (Google Slides, a PDF, a separate
static site) and the packaging story breaks: two links, two deploys, two places
to version.

The target: the catalog landing page shows cards for **one workshop's worth of
material** — card 1 is the slide deck, card 2 is the lab — and both are the same
build, the same repo, the same `docker run`. The deck is markdown-driven like
everything else, rendered in-app (reveal.js or similar), and can drop a **live
simulated terminal into a slide** for demos, driven by the same simulator engine
the lab uses.

## 2. The headline: this is cheaper than it looks

The app is already structured for it, in three ways that matter.

**The catalog is already a generic typed list.** `labs.json` is generated by
`app/scripts/catalog.mjs` from any directory under `labs/` containing a
`labspace.yaml`. Add one field to the emitted entry and the landing page can
render two kinds of card. Nothing about discovery, the `?catalog=` override, the
deploy workflow, the starter's Dockerfile, or pulse's `labId` bucketing has to
move.

**The context stack is decoupled from the lab layout.** Walking
`AppRoute.jsx` → `WorkshopContext` → `TabContext` → `TerminalContext` →
`TrackingContext`, the providers only ever read a handful of fields off the
loaded object: `terminals`, `services`, `features`, `files`, `simulatorSpec`,
`variables`, `sections`, `labKey`. They never assume a two-pane layout. So if the
deck loader returns a **workshop-shaped object**, the entire provider stack is
reusable verbatim and only the _view_ changes.

**The markdown renderer is the valuable part, and it's portable.**
`MarkdownRenderer` is already used by two different views (`WorkshopPanel` and
`ExportView`). It carries GFM, mermaid, GitHub alerts, `$$variable$$`
substitution, and the whole directive set (`:filelink`, `:tablink`,
`:variabledefinition`, `:conditionaldisplay`) plus `CodeBlock` with its
Run/Copy/Save buttons. A deck should render slide bodies through _this_, not
through reveal.js's own markdown plugin — see §6.

Two smaller pieces of luck: `PanelWindow` already portals the terminal pane into
a real second browser window (its placeholder literally says "Keep that window on
screen while you present"), which is most of a presenter setup already; and
adding a `::terminal{…}` directive is a two-line change given
`reactDirective.js`.

## 3. What it would look like to an author

A deck is just another directory under `labs/`, so the unit of packaging stays
"a directory you can mount".

```
labs/
  containers-101-slides/      ← the deck
    labspace.yaml
    01-why-containers.md
    02-primitives.md
    03-live-demo.md
  containers-101/             ← the lab
    labspace.yaml
    simulator.yaml
    00-intro.md
    ...
```

### The manifest

```yaml
# labs/containers-101-slides/labspace.yaml
kind: slides # NEW. Absent → "lab", so every existing lab is unchanged.
title: "Containers 101"
description: "The 20-minute version, before you get your hands dirty."

catalog:
  icon: slideshow
  order: 1 # deck first, lab second, on the landing page
  estimatedMinutes: 20

# OPTIONAL — only if a slide runs a live demo. Pointing at the SIBLING LAB's
# spec means the demo runs the exact commands the learners are about to run.
# Paths already resolve relative to this file, so `../` works as-is.
simulator: ../containers-101/simulator.yaml

theme: docker # NEW (deck-only)
transition: slide # NEW (deck-only)

slides: # alias of `sections:` — same loader code path
  - contentPath: 01-why-containers.md
  - contentPath: 02-primitives.md
  - contentPath: 03-live-demo.md
```

### The slide markdown

One file per _chapter_, split into slides on a `---` rule. That's reveal.js's own
convention, so it's familiar, and it means a chapter reads as a normal markdown
document.

````markdown
# Why containers?

Ship the environment, not just the code.

Note: Ask the room who hit "works on my machine" this week.

---

## Three primitives

- **Image** — the build artifact
- **Container** — a running instance
- **Registry** — where images live

---

## Let's try it

::terminal{id=demo height=340}

```bash
docker run -d -p 8080:80 nginx
```
````

`Note:` is reveal's speaker-notes convention. The `::terminal` directive mounts a
`<MockTerminal>` bound to the shared simulator; the code fence above it keeps its
normal **Run** button, so the presenter clicks Run and the scripted output
streams into the slide.

## 4. The in-slide terminal

This is the part with genuine design choices, not just plumbing.

The mechanism is settled: `TerminalContext` already owns exactly one `Simulator`
for the whole entry and hands out imperative `runCommand` / `saveFile` handles by
id, and `MockTerminal` is a self-contained component that takes a `simulator`
prop. A `::terminal{id=demo}` directive resolves to the same thing a terminal tab
resolves to today. The persistence, transcript restore, reset broadcast, and
Run-button wiring all come along for free.

What needs deciding is **where the terminal lives on screen**:

- **Inline in the slide** (as sketched) — best for teaching, since the command
  and its output sit next to the prose. Costs vertical space and every slide with
  a demo has to be laid out around it.
- **A persistent bottom/side rail** the presenter reveals with a key — the deck
  stays clean, one terminal for the whole deck, demo state accumulates across
  slides.
- **Popped out via `PanelWindow`** — deck on the projector, terminal on the
  laptop. Already built; the strongest presenter story and the cheapest of the
  three.

These aren't exclusive; inline is the most work and the rail is probably the
better default for a real presentation. Worth trying inline first only because
it's the one that demos well in a screenshot.

Two concrete gotchas, both about focus:

- **Keyboard contention.** reveal.js binds arrows/space/`?` globally. It skips
  handling when focus is inside an `input`, which covers normal typing — but
  `MockTerminal` _unmounts its input row while output streams_ (`{!busy && …}`),
  so keystrokes during a streaming demo would fall through and advance the slide.
  Needs an explicit guard (a `data-prevent-swipe` / `keyboardCondition` scope
  around the terminal, or keep the input mounted-but-disabled).
- **Reset semantics.** A deck's simulator state persists in `localStorage` under
  the entry id. A presenter rehearsing then presenting wants a one-key "reset the
  demo" — `resetAll()` exists, it just needs a deck-chrome button.

## 5. Should the deck and lab share simulator state?

Recommendation: **no — independent state, shared spec.** The deck points at the
lab's `simulator.yaml` (so the demo and the exercise can't drift), but each entry
keeps its own `simspace:engine:<id>` namespace.

Sharing live state across entries would mean a learner arriving at the lab with
the demo's containers already running, which breaks both the reset story and the
per-entry isolation the catalog spec promises. If "carry the demo forward" ever
becomes a real ask, it's a separate feature (an explicit state hand-off), not a
side effect of packaging.

## 5a. Prerequisite: extract the terminal into a package first

Raised separately, but it lands here: the simulator + terminal are also wanted in
**docs and the www site**, surfaces that need none of the instructions, pulse, or
slide machinery. That turns out to be nearly free, and it changes the sequencing
of the deck work.

The dependency cone is already clean:

- **`app/src/engine/`** (12 files, ~1,500 lines TS) has exactly **one** external
  dependency (`yaml`, in `manifest.ts`) and **zero** DOM/browser/Node access.
  `new Simulator({ spec, files?, restoredState?, restoredFiles? })` is a pure
  string-in constructor, and `checkSchemaVersion` already gates on the `2.x`
  major — so a published package has a compatibility contract on day one.
- **`MockTerminal.tsx`** imports React, two engine types, `Simulator`, and
  `scopedKey` — a three-line pure function. `MockTerminal.css` is fully
  self-contained (own custom properties, system monospace stack, no Bootstrap, no
  webfont).
- **Four import sites in the entire app**: `TerminalContext` and `MockTerminal`
  take `Simulator`; `TerminalPanel` takes `MockTerminal`; `validate-lab` takes the
  engine index. `CIPanel` / `SettingsPanel` reach the engine only through
  `useTerminal()`.

Genuinely coupled, and the whole list:

1. **Persistence.** `MockTerminal` does its own `localStorage` I/O from a `labKey`
   prop. A docs-page terminal shouldn't persist across reloads. Swap `labKey` for
   an optional `storageKey` / pluggable store, defaulting to none. This is the one
   real API change.
2. **Simulator construction.** `TerminalContext` owns spec→Simulator, restore,
   pub/sub, the handle registry, and `resetAll`, mixed with lab concepts
   (`resetVariables`, `labKey`). The package needs that logic minus the vocabulary.
3. **The N-terminals-share-one-Simulator model** is a lab need; docs want 1:1. So
   export both layers.

Suggested shape — one package, three entry points:

```
simspace-simulator          → pure engine (dep: yaml). Also what validate-lab imports.
simspace-simulator/react    → <MockTerminal> + CSS (peer: react)
simspace-simulator/element  → <sbx-terminal spec="…"> for non-React surfaces
```

The cost is not the code split (~1–2 days as an in-repo workspace package the app
consumes; +1–2 days to be genuinely publishable; +1 day for the custom element).
The cost is **tests**: `AGENTS.md` is explicit that there is no unit-test suite,
which is defensible for one app and a different risk posture when a regression
ships to three surfaces. Budget 2–3 days for engine coverage and don't skip it.

**New blocking question: what are docs and www built with?** If either is
Hugo/Docusaurus/plain HTML, a React package with a React 19 peer dep is a hard
sell and the custom element is the _primary_ artifact, not a nice-to-have.

**Why this comes first.** Extraction doesn't reduce the deck work — the deck needs
the terminal either way. But if the deck is built against app internals, the
extraction gets paid for twice. Do it first and make the deck the package's
**first consumer**: `::terminal{}` then integrates through exactly the public API
docs and www will use, validating the contract before it ships to surfaces we
don't control.

Worth noting for the "are we overloading the app?" worry: the terminal is _not_
the accumulation risk — it's already isolated. The accumulation is in the app
shell (`App.jsx`'s route table, `Home.jsx`'s dispatch, `WorkshopContext`'s loader
doing double duty), which is exactly what a deck adds to. That's the argument for
keeping deck chrome in its own route rather than teaching `WorkshopPanel` a second
mode.

## 6. The integration risk: reveal.js inside React

This is the one thing I'd want a spike on before committing to an estimate.

**Do use reveal.js for chrome only.** Its markdown plugin (marked-based, owns its
own DOM) would cost us the entire existing renderer — Run buttons, mermaid,
directives, variable substitution. Instead: React renders
`.reveal > .slides > section`, each `<section>`'s children rendered by
`MarkdownRenderer`, and reveal is initialized over that DOM in a `useEffect`.
Reveal 5.x instances are scoped (`new Reveal(el, opts)`) and it operates on
pre-existing DOM, so this is its supported path — but it does mutate what it
manages (`class="past/present/future"`, `hidden`, `aria-hidden`, `style` on
`.slides`, an injected `.backgrounds` sibling), and `Reveal.sync()` must be called
if the slide list changes. Render slides once, keyed on the deck, and don't
reorder them.

**The routing conflict is the concrete one.** Reveal's `hash: true` writes
`#/2/1` into `location.hash` — and the app uses `HashRouter`. These will fight
over the hash and produce navigation loops. Fix: initialize reveal with
`hash: false, history: false` and make the router the single source of truth,
driving reveal from the route and pushing routes from reveal's `slidechanged`
event.

**What we'd get for the dependency:** fragments (incremental reveal), transitions,
overview mode, auto-scaling text, a speaker-notes window with a timer, and
`?print-pdf` export. That's a lot of workshop-grade behaviour we would otherwise
hand-roll.

**The alternative worth pricing:** a ~250-line home-grown slide layer. Keyboard
nav, fragments, a progress bar, fullscreen. No DOM-ownership conflict, no hash
fight, full control, and it reuses `PanelWindow` for notes instead of reveal's
notes plugin. It loses transitions, overview, and PDF export. Given this repo's
strong "own the primitives" streak (its own terminal, its own engine, its own
popout window), this is a more serious option than it would be elsewhere — and
the print story is arguably already solved by `ExportView`.

I'd spike the reveal path for a day. If the hash/DOM friction bites, the
home-grown layer is a known quantity.

**Estimate:** Phase 1 is half a day. Phase 2 is ~3–4 focused days for a v1 with a
sample deck and specs, _plus_ the one-day reveal spike up front — call it a week,
with the spike as the only real schedule risk. Speaker notes, PDF export, and
cross-entry hand-off links are a deliberate phase 3.

Nothing here is a breaking change: `kind` defaults to `lab`, every existing
`labspace.yaml` keeps working untouched, and a repo with no decks behaves
identically.

## 8. Decisions I need from you

Ordered by how much they change the work.

1. **reveal.js, or a small home-grown slide layer?** (§6) The single biggest fork.
   Concretely: do we need transitions, overview mode, and reveal's speaker-notes
   window badly enough to take the DOM/hash friction?
2. **Presenter-facing, learner-facing, or both?** This drives speaker notes,
   whether "completed the deck" means anything for the catalog badge, and whether
   a deck should emit tracking events at all. A deck an instructor presents to a
   room is noise in pulse; a deck a self-paced learner reads is signal.
3. **Where does the demo terminal live** — inline, rail, or popped out? (§4)
4. **One manifest name or two?** `labspace.yaml` + `kind: slides` keeps discovery,
   validation, both deploy paths, and the starter template untouched — but the
   filename reads wrong for a deck. The alternatives are a second discovered
   filename (`slidedeck.yaml`), or renaming the manifest to something neutral
   with a fallback. I lean `kind:` for v1 and treat the rename as its own change.
5. **Flat catalog or real collections?** `catalog.order` already gets you "deck
   card first, lab card second". A genuine `collection:` grouping — landing-page
   section headers, a "Continue to the lab →" hand-off on the last slide, cross-
   entry links — is additive but is a separate design.
6. **URL space.** Keep `#/labs/<id>` for decks (dispatch on kind, so pulse ids,
   deep links, and `?catalog=` don't move) or introduce `#/decks/<id>`?
7. **Slide splitting.** `---` within a chapter file (reveal-native, needs a
   fence-aware splitter), one file per slide (zero new parsing, 40 files), or
   both? Related: do we want reveal's `<!-- .slide: … -->` per-slide config
   comments, or a cleaner directive?

One naming note worth deciding early even though it isn't blocking: `labs.json`,
`labs/`, `labId`, `labKey`, `simspace:engine:<lab>`, `/labs/:labId` all become
slight misnomers. I would **not** rename any of them — they're baked into
deployed URLs, saved learner progress, and pulse's stored data — but new code
should use a neutral word ("entry"), and we should agree on which one so the
vocabulary doesn't fork twice.
